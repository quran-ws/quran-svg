# The ayah polygon layer, as it actually ships

Three things about the polygon layer are not guessable from one page, and each of
them is a bug a consumer only finds later. Every figure here was measured against
this repository.

## 1. The polygons are beneath the glyphs in four muṣḥafs and on top in Ḥafṣ

In `svg/NNN.svg` the ayah polygons and the page glyphs are siblings at the root of
the document, so which one receives a click is decided by document order alone.
That order is **not the same across muṣḥafs**:

| Muṣḥaf | `ayahPolygon` paths | Painted | A click lands on |
|---|---|---|---|
| `hafs/kfqc` | **after** the glyphs | on top | the polygon |
| `warsh/kfqc` | **before** the glyphs | beneath | the glyph |
| `qalon/kfqc` | **before** the glyphs | beneath | the glyph |
| `douri/kfqc` | **before** the glyphs | beneath | the glyph |
| `shubah/kfqc` | **before** the glyphs | beneath | the glyph |

It is unanimous within each muṣḥaf — all 722 pages of each, no page interleaved.

So **give the glyph paths `pointer-events: none`**:

```css
.ayahPolygon { fill-opacity: 0; cursor: pointer; }
svg path:not(.ayahPolygon) { pointer-events: none; }
```

Without it, hit-testing works perfectly in Ḥafṣ and fails on every other riwāyah —
clicks land on the letter ink wherever there is ink, and reach the polygon only
through the whitespace between glyphs. Ḥafṣ is the muṣḥaf everyone develops
against, so this is a bug that ships. If you are testing the hit layer, test it on
Warsh.

The polygons are root-level children of `<svg>` in every muṣḥaf, in the page's own
unflipped coordinates. Only the sibling order differs — the glyphs sit inside a
`<g transform="matrix(…)">` page frame whose y axis is flipped, the polygons never
do.

## 2. The `polygon` field in `json/NNN.json` ships in two shapes

In the SVG an ayah's hit-region is always path data in `d`. In the JSON it is not:

```jsonc
// pages 3 and after — SVG path data, one subpath per line the ayah occupies
"polygon": "M 0.0 0.75 L 337.75 0.75 L 337.75 41.0 L 0.0 41.0 Z M 254.12 41.0 … Z"

// pages 1–2 — a bare `x,y x,y …` point list, no commands
"polygon": "181.08,18.31 57.54,18.31 57.54,48.94 181.08,48.94"
```

Page 3 onwards is generated by `tools/build_ayah_polygons.py`, which builds an ayah
out of the line bands it covers — an ayah spanning three printed lines is three
rectangular subpaths. The ornate opening spread, pages 1–2, is [out of scope for
that generator](../tools/README.md) and keeps a single hand-corrected staircase per ayah, written as a
point list. It is a small set and the same in every muṣḥaf: 11 or 12 point-list
polygons per muṣḥaf, 7 on page 1 and 4–5 on page 2, against ~8,260 path-data ones.

A parser written against page 1 produces `NaN` on page 3. Handle both:

```js
// json `polygon` → SVG path data, either shape
function polygonToPath(polygon) {
  if (polygon.trimStart().startsWith('M')) return polygon;   // already path data
  const n = polygon.match(/-?\d+(?:\.\d+)?/g).map(Number);   // "x,y x,y …"
  const pts = [];
  for (let i = 0; i < n.length; i += 2) pts.push(`${n[i]} ${n[i + 1]}`);
  return `M ${pts.join(' L ')} Z`;
}

// json `polygon` → bounding box, either shape
function polygonBBox(polygon) {
  const n = polygon.match(/-?\d+(?:\.\d+)?/g).map(Number);
  const xs = n.filter((_, i) => i % 2 === 0), ys = n.filter((_, i) => i % 2 === 1);
  return { x: Math.min(...xs), y: Math.min(...ys),
           w: Math.max(...xs) - Math.min(...xs), h: Math.max(...ys) - Math.min(...ys) };
}
```

Pulling every number out and pairing it as `x,y` is safe for a **bounding box**,
because the path commands carry no coordinates of their own. It is not safe for an
outline: joining the pairs across subpath boundaries welds separate printed lines
into one ring. To draw the shape, keep the path data as it is.

## 3. On pages 1–2 the declared box is not the ink

Every page declares a 345 × 550 `viewBox`, but the opening spread fills about a
fifth of it. Measured union of each page's ayah polygons:

| Muṣḥaf | page 1 | page 2 | page 3 |
|---|---|---|---|
| `hafs/kfqc` | 222 × 197 — 23.0% | 217 × 170 — 19.5% | 338 × 548 — 97.5% |
| `warsh/kfqc` | 222 × 192 — 22.5% | 224 × 195 — 23.0% | 331 × 537 — 93.7% |
| `qalon/kfqc` | 222 × 192 — 22.5% | 224 × 195 — 23.0% | 331 × 538 — 93.8% |
| `douri/kfqc` | 225 × 178 — 21.0% | 223 × 177 — 20.8% | 338 × 546 — 97.3% |
| `shubah/kfqc` | 222 × 197 — 23.0% | 217 × 170 — 19.5% | 338 × 548 — 97.6% |

Percentages are of the 345 × 550 box. Pages 1–2 also carry a `viewBox` with a
non-zero negative origin (`-53.31 -198.48 345 550` in Ḥafṣ) where page 3 onwards
starts at `0 0` — read the `viewBox`, never assume it.

So a render that fits the `viewBox` puts the opening spread in a box three quarters
empty. If you are cropping or fitting a single page rather than laying out the full
spread, measure it — the rendered `getBBox()`, or the union of that page's polygon
bounding boxes — instead of trusting the declared box.
